# Privacy controls for operational acceptance

Ordinary application events use the reviewed allowlist of fixed action/provider/result codes and correlation/release identifiers. Do not copy credentials, feed URLs, OAuth code/state/verifiers, cookies, authorization headers, raw provider bodies, user IDs/emails, or assignment/course content into logs or acceptance evidence. Error propagation and service-unavailable classification are distinct: an unrelated exception must not produce a false storage-outage metric.

Production persistent logs, invocation metadata and traces remain disabled. Application redaction tests and the controlled preview assessor do not prove platform/framework stored-log behavior or retention. The complete stored-log/privacy gate remains unverified; keep persistence off until that evidence is reviewed. See the retained 7C task 3 privacy capture plan and current deployment configuration.

Local auth fixtures report finite request counts only. They require explicit HTTP loopback fixture bindings; known Turnstile test keys and fixture promotion are rejected by production validation/runtime. A provider-request count proves which controlled transport was exercised, not real provider consent or identity success. Browser trace and response captures from these tests contain synthetic data only; do not reuse that capture pattern with real credentials or identities.

Credential envelopes, onboarding candidates and pending PKCE remain encrypted and scoped to user/purpose/context. Rate history contains derived keys and has bounded expiry cleanup. Expiry alone is not immediate deletion: scheduler delays/backlogs extend retention, and live/uncertain owner metadata is deliberately retained until settlement. Cleanup bounds, scans, FK cascades and activation evidence are documented in [monitoring](monitoring.md#admission-measurements-and-release-handoff) and [incident response](incident-response.md). Account deletion and provider-grant revocation remain separate controls and require real hosted acceptance before launch.

## Recovery access, deleted accounts and key retention

October 15 evidence: account-member metadata reports one accepted Super Administrator. The operator confirms no D1-access API tokens, no external database backups/exports, possession of the original credential key and sole export/restore authority. The owner's existing Wrangler OAuth session is distinct from an API-token inventory; read-only preflight used it without exporting or restoring data. No CI deployment credential has been provisioned. Adding a delegate, API token or external backup requires a new access/retention review.

The operator reports Workers Free. Cloudflare documents [seven days of D1 Time Travel on Free and 30 on Paid](https://developers.cloudflare.com/d1/reference/time-travel/); bookmarks are automatic recovery history, not copies that disappear with live account deletion. Do not promise immediate historical erasure. Record plan changes and any new exports, and review the privacy notice before changing retention. Do not retire a credential key while any live envelope or retained recovery point needs it; retain the original v1 key through the applicable recovery horizon after the final v1 write and longer if an authorized copy still depends on it. A zero live old-key count alone is insufficient.

Database restoration is an **owner-only disaster operation**, separate from ordinary code rollback and requiring its own explicit approval. The following policy applies before reopening any restored state:

1. Quiesce/contain server and browser work and keep the restored service inaccessible. Privately capture a verified inventory of currently live user IDs immediately before restoration. Treat it as restricted operational data, not a log, repository artifact or chat attachment. If the current live/deletion inventory cannot be established, keep the service closed until an authoritative deletion record can be recovered; do not reopen a historical snapshot blindly.
2. After the owner restores, compare recovered users against that pre-restore live inventory. Remove every recovered account absent from the verified live inventory, including its identity links, sessions and FK-owned data. Use exact parameterized account deletions and verify cascades. This prevents a recovery point from reviving an account already deleted before restoration. Inspect the result privately; do not publish identifiers or coursework.
3. Invalidate all recovered sessions before reopening so previously signed-out/revoked database bearers do not become valid again. Pause provider controls with version changes, quarantine unsettled ownership, and review restored source/calendar connections, saved drafts and authorization requests against current user intent. A snapshot is not proof that an earlier disconnect, draft discard or provider revocation remains authorized. Require reconciliation/renewed user authorization where current state is unknown; do not resume external writes automatically.
4. Verify the restored schema and required keys, then apply only reviewed forward migrations if needed. Preserve uncertainty/cooldown and independently establish settlement before targeted owner recovery. Never erase ownership or run down migrations merely to reopen.
5. Test deletion preservation, fresh sign-in, tenant isolation and provider state before the owner reopens access. Keep the restricted inventory only as long as recovery verification needs it under the owner's custody. Record aggregate outcomes and source/config identities, not the inventory itself. No agent database export/restore or live restore success is implied by this procedure.
